## What we are building (v1)

Volume they reported: about **15–20 leads/day** and **~60 conversations/day**. About 70% of leads interact outside office hours.

1. **WhatsApp assistant** on the official API number (marketing/cloud number), reached through **Kapso**, a Business Solution Provider for the official WhatsApp Cloud API (decided Oct 2026; Altamira agreed; due diligence in the Project store, `docs/whatsapp-options.md`). Conditions: Altamira's own number (never a Kapso-provided one), the WhatsApp Business Account in Altamira's own Meta Business portfolio, Meta paid by card directly (not Kapso credits), and Kapso message retention at 30 days on a paid plan. Greeting, then the information to collect that each company configures (for Altamira: interest, budget, whether they know the projects; all required), which the bot finds out naturally, in any order, without re-asking what the lead already said, answers to repeated questions (price-from, typology, delivery date, orientation). A lead who writes gets the greeting; a lead who arrives from a form gets one welcome. A lead with no interest is written to the CRM and no advisor is assigned. No future rental-yield or “guaranteed rent” answers. No project-presentation file in v1.
2. **Knowledge** from files operators upload in the backoffice, per company. Formats: PDF, Word (DOCX, DOC), Excel (XLSX, XLS), OpenDocument (ODT, ODS), PowerPoint (PPTX), CSV, plain text, Markdown, HTML, and JSON. Text is extracted on upload, stored in Postgres, and injected into the prompt. Commercial facts (price-from, typology, delivery, orientation) come from those files. Re-uploading a file replaces its previous version; if they do not re-upload, prices go stale. Default limits (company config): **60,000 characters of text per file**, **150,000 per company**, **15 MB per upload**. Operators can preview the extracted text. Allowlisted public site pages are optional and secondary (address, amenities), and not built in the MVP. No RAG, no embeddings, and no live browsing during a chat. Uploaded files win over site notes on commercial facts. Do not dump full inventory or unit-level availability in chat. Google Drive / Sheets sync and a Connect Google OAuth flow are later. MCP is not the plan.
3. **HubSpot Sales Pro** (already live ~2 months). On handoff, close, or when the bot stops itself and waits for a person, create/update the contact and write one long text property via the HubSpot API: the assistant's bullet summary and the collected fields at the top, then the transcript. No per-field properties. Failed writes retry with backoff and show in the panel. Do not use HubSpot’s native AI (José estimated that route at about USD 1,800/month at this volume).
4. **Handoff:** if the lead qualifies, ask when an advisor can call, then leave the case for the team. Advisors keep their own WhatsApp numbers. The bot does not live on those phones.
5. **Small panel:** thread list and the ability to pause the assistant when a human takes over. The Conocimiento page is upload, list, replace, and delete files, not a sheet sync. The sidebar is Conversaciones, Conocimiento, and Configuración (plus Empresas for a platform admin). Configuración is where any operator of the company (no admin/member roles in the MVP; a platform admin through support access too) edits everything in the company config (tone, the information to collect (up to 10 items, each a key, a name, a short description for the prompt, and required or optional), forbidden topics in plain language (no regex patterns), fixed messages, business hours, welcome template, HubSpot property name, model and knowledge limits), validated before saving; Idioma, Zona horaria (IANA), País de los teléfonos (country and calling code), and Modelo de Anthropic are searchable selects, the models listed from Anthropic's API when the company has its key and from a fixed list otherwise, and a saved value outside the list stays valid), the WhatsApp phone number id (a unique column on the company that routes inbound webhooks; empty until the company has a number), and the company instructions (free text). The platform rules the engine depends on (the submit_turn output format, the required-items handoff, the needsHuman and forbidden-topic flags, the 24-hour window) stay in code and are shown read-only, next to the full prompt the model would receive. Each save of the config, the instructions, or the phone number id keeps a version with who and when, and any version can be restored. Configuración is laid out as a grouped section nav (Asistente: General, Conversación, Temas prohibidos, Mensajes fijos, Bienvenida y CRM, Modelo y límites; Prompt: Instrucciones, Reglas y prompt; Empresa: Integraciones, Historial, and Operadores for support access), one section at a time, with one config draft across the Asistente sections and a save bar that shows only with unsaved changes. Integraciones is a section (tab) of Configuración where an operator connects WhatsApp through Kapso (the Phone number ID, a Spanish step-by-step guide, the company's exact webhook URL with a copy button, and Probar conexión, which asks Kapso for the number's health and the webhook that points at the company) and sets that company's secrets (Kapso API key, Kapso webhook secret, Anthropic API key, HubSpot access token, form-lead secret); the old `/integrations` route redirects there. Write-only: the panel shows whether each is set and the last 4 characters when that does not reveal the whole value, never the full secret. An empty field does not clear one; Quitar does. `SECRETS_ENCRYPTION_KEY` stays a server env var. `npm run company:secret` remains for debugging. Empresas is a platform-admin page: the signed-in Supabase email must be on `PLATFORM_ADMIN_EMAILS` (comma-separated, not hardcoded). That login can open it with no operator row and no companies. It creates a company (row, slug, starter config, first operator email) and lists existing companies, archived ones behind Mostrar archivadas. Empresas itself does not collect API keys. Archiving a company blocks its operators (403 with a Spanish reason), refuses support access into it, makes the WhatsApp webhook ignore its number (nothing stored, no reply), and makes its form-lead hook 404; Restaurar undoes it. Eliminar asks for the slug typed back and removes the company and its data by cascade. Operators of a company are managed from Empresas (Operadores) or inside it through support access (Configuración → Operadores, admin only): adding one saves the row, then creates the Supabase Auth user and sends Supabase's invitation email to `/auth/set-password` on the panel that sent the request (its Origin when it matches `BACKOFFICE_ORIGIN`, a comma-separated list that may use one `*` in the first host label for Render PR previews; otherwise the first exact entry) through the Supabase admin API with `SUPABASE_SERVICE_ROLE_KEY` (server env only); an existing Supabase user with that email is linked instead; a failed invite keeps the row with a Spanish reason and can be resent (resend to an account that already has a password sends the password-reset email). Archiving an operator blocks that login until restored (the API refuses it; the Supabase user is not banned). Deleting one removes the row and its Supabase user, unless that login is still an operator elsewhere or on `PLATFORM_ADMIN_EMAILS`. In `AUTH_MODE=dev` an in-memory stand-in replaces Supabase. The first operator of a new company is invited the same way. Each company row has Entrar (support access): the panel then sends `X-Company-Id` on every API request, and the API honors it only when the signed-in email is on `PLATFORM_ADMIN_EMAILS`. For everyone else the company always comes from their operator row and the header is ignored. The admin needs no operator row in that company and sees its Conversaciones, Conocimiento, and Integraciones (still write-only for secrets), under a bar that says "Viendo como administrador: <empresa>" with Volver a Empresas. Every write made through support access, and every Empresas write to an existing company (archive, restore, delete, operator changes), is recorded in `AdminAuditEntry` (admin email, company id and slug, method and path, status, time); entries survive the company's deletion with the slug; there is no screen to browse it yet. Operators who are not on the list get no nav item and 403 on the routes. After they are created, they sign in only to their company. `db:seed` and `operator:add` stay as local fixtures; a production setup does not run them.

## Product rules

- Model: Anthropic `claude-haiku-4-5`, behind one `complete()`. Behavior will need live tuning; tests alone will not catch bad answers.
- Never answer future rental yield or guaranteed returns.
- Price-from and typology are allowed. Full availability stays with the advisor.
- Knowledge changes often (units, prices, quotas). Uploaded files are the commercial source, not a prompt frozen at kickoff. Re-upload replaces the previous file; prices go stale if they do not. Public site notes are optional and for stable facts only. Commercial facts in the uploaded files win over site notes.
- Two WhatsApp worlds: API number for the bot, personal numbers for advisors. Do not merge them in v1.
- The model returns structured fields through `submit_turn` (reply, collected values by item key, call time, intent with an explicit not-interested, needsHuman, a forbidden-topic flag, and a short bullet summary of the conversation and what the lead wants, stored on the thread every turn); the engine owns the conversation state. Handoff starts only once every required item is stored; optional items never hold it. The thread's Lead panel shows the summary and the collected fields.
- When a lead asks something only a person can answer (a complaint, an existing purchase, insisting on a person), the model flags a forbidden topic (the lead asked about one or its reply would touch one), or the model or WhatsApp fails, the bot stops itself (`needsHuman`), the engine sends one fixed line from company config (never the model's own words on a forbidden topic), writes HubSpot, and waits until an operator marks the thread attended. Forbidden topics are plain language only; there is no regex check on replies.
- Nothing Altamira-specific is hardcoded: tone, the information to collect, forbidden topics, knowledge sources, and CRM settings live in company config, and the company's own instructions live on the Company row. The system prompt is platform rules (in code, filled from the config), then the company instructions, then the knowledge block; the platform rules win if they disagree.

## Stack (v1)

One repo, two apps: `backend/` (Express 5 + Prisma 7 + Anthropic + WhatsApp + HubSpot, deployed as a Docker container) and `backoffice/` (client-side Next.js 16, shadcn with preset `b1Z5bafVA` on the `dashboard-01` layout, Tailwind 4, React Query). One controller and one service per endpoint; services call Prisma directly. Supabase provides Postgres and Auth; Prisma owns the schema and all DB access from the backend. Local development uses Postgres (Docker Compose is the stand-in). Supabase and the app host are in **us-east-1**. WhatsApp goes through Kapso, not Meta Cloud API direct: each company has its own Kapso project, its Kapso webhook posts to `/webhooks/kapso/<company slug>` and is verified with that company's webhook secret (hex HMAC-SHA256 in `X-Webhook-Signature`), and replies and the welcome template go to Kapso's WhatsApp API (Meta's body, `X-API-Key`). The channel sits behind an adapter so another provider could be added; Kapso is the one that ships. There is no platform-wide WhatsApp env var. Per-company Anthropic, Kapso, HubSpot, and form-lead secrets are encrypted on the Company row (AES-256-GCM). An operator sets them for their own company from Configuración → Integraciones in the panel (a platform admin can too, through support access); the API never returns the full value. The encryption key stays in the server environment. No Vault in v1. Google access is later, with Drive / Sheets. One shared deployment for all companies; the same image can be deployed separately if a client needs isolation. Knowledge is text extracted from files operators upload, stored in Postgres per company, then injected into the Anthropic prompt (no RAG). Optional allowlisted site pages are secondary. Details: `docs/design.md`.
